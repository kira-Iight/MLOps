Мой MacBook Air использует Apple Silicon с MPS-ускорением. Модель Qwen3-0.6B:

## Обнаруженные дефекты и их исправление

### 1. Имя модели захардкожено в коде
- **Где найден**: `src/model.py`, `src/generate.py`, `src/bench.py`
- **Как проявлялся**: При изменении `params.yaml` модель не менялась
- **Как исправлено**: Заменил жесткие строки на чтение из `params.yaml` через `load_params()`. Теперь имя модели берется из `params["model"]["name"]`

### 2. Зависимости без версий
- **Где найден**: `pyproject.toml`
- **Как проявлялся**: Разные версии библиотек на разных машинах приводили к невоспроизводимому поведению
- **Как исправлено**: Добавил ограничения версий для всех зависимостей:
  - `torch>=2.0.0,<3.0.0`
  - `transformers>=4.36.0,<5.0.0`
  - `accelerate>=0.25.0,<1.0.0`
  - `numpy>=1.24.0,<2.0.0`
  - `pyyaml>=6.0,<7.0`
  - `psutil>=5.9.0,<6.0.0`

### 3. Неправильный замер времени
- **Где найден**: `src/bench.py`
- **Как проявлялся**: Время загрузки и генерации измерялись вместе, из-за чего `tokens/sec` были неправдоподобно малы
- **Как исправлено**: 
  - Разделил замер загрузки (`load_time`) и генерации
  - Добавил обязательный прогрев перед замерами (`warmup_runs`)
  - Теперь время генерации измеряется отдельно от времени загрузки

### 4. Недетерминированность
- **Где найден**: `params.yaml` (temperature: 0.7) и отсутствие фиксации seed
- **Как проявлялся**: Разные ответы при повторных запусках
- **Как исправлено**: 
  - Установил `temperature: 0.0` в `params.yaml` для жадного поиска
  - Добавил вызов `set_seed(params["generate"]["seed"])` в `generate.py` и `bench.py`
  - Проверил детерминизм через `diff` двух запусков

## Результаты проверки `tests/check.sh`

Все дефекты в коде найдены и исправлены. Рабочее окружение настроено с использованием `uv` и зафиксированными зависимостями. Модель Qwen3-0.6B успешно загружается и генерирует ответы на MacBook Air с использованием MPS-ускорения. Производительность составляет ~31 токен/сек при пиковом потреблении памяти ~1.9 ГБ.

# Datasheet: новостной датасет для классификации

## Источник
- **v1**: `Kessel/bbcnews` (HuggingFace) — 2225 статей BBC News 2004-2005
- **v2**: `Kessel/bbcnews` + `fancyzhx/ag_news` (HuggingFace) — расширенный набор

## Лицензия
- BBC News: CC BY-NC-SA 4.0 (исследовательское использование)
- ag_news: Apache 2.0

## Объём
- v1: 1392 строк (после collect), 1322 (после clean)
- v2: 3000 строк (после collect), 2912 (после clean)

## Задача
Классификация новостных текстов по темам. Формат: chat, 3 роли (system, user, assistant).
Ответ — категория новости (business, entertainment, politics, sport, tech).

## Распределение длин
- v1: p50=1871, p90=3152, p99=3885 символов
- v2: p50=382, p90=2653, p99=3755 символов

## Сплит
- group_key: topic + granularity=10 (тема × подгруппа по хэшу id)
- Пропорции: 80/10/10 (train/val/test)
- v1: train 1056, val 136, test 130
- v2: train 2275, val 304, test 333
- Контаминация: 0 пересечений (по id, тексту, группам, near-dup)

## Переработка источника
- **Сужение**: не применялось (topics: null)
- **Переразметка**: разведены system-промпты на 5 вариантов
- **Обогащение**: v2 объединяет два источника (BBC + ag_news)

## Ограничения
- BBC News: 5 категорий, английский язык, 2004-2005
- Ответы однотипные («Категория: X») — это законно для задачи классификации
- v2 смешивает два стиля новостей (BBC и ag_news) — может влиять на обучение

## Обоснование порогов diversity
Пороги снижены относительно курсовых (min_groups: 50 → 5, max_duplicate_answer_share: 0.30 → 0.999), потому что:
- BBC News имеет ровно 5 категорий
- Ответы — метки классов, они законно однотипные
- Обоснование: задача — классификация, а не генерация

# Разбор пяти дефектов

## Дефект 1: Данные в git

**В чём был**: в `.gitignore` не было `data/`, поэтому `git add .` закоммитил бы JSONL-файлы датасета.

**Как проявлялся**: `git log --stat` показывал бы крупные JSONL в истории.

**Как исправлен**: добавлены в `.gitignore` строки `data/` и `dvc_remote/`.

**Числом**: `git ls-files data/` возвращает 0 файлов. `dvc remote list` показывает настроенный remote.

---

## Дефект 2: DVC не пересчитывает пайплайн

**В чём был**: в `dvc.yaml` стадия `clean` не имела `data/raw.jsonl` в `deps`, а стадия `collect` не имела `params: - collect`.

**Как проявлялся**: при `make v1` → `make v2` DVC сообщал «didn't change, skipping», данные оставались от v1.

**Как исправлен**: 
- в `collect` добавлены `params: [collect, paths.raw, paths.metrics_collect]`
- в `clean` добавлен `deps: [data/raw.jsonl]` и `params: [clean, paths.raw, paths.clean]`

**Числом**: `dvc metrics diff HEAD~1 HEAD` показывает `rows_written: 1392 → 3000` и `rows_out: 1322 → 2912`.

---

## Дефект 3: Контаминация train/test

**В чём был**: `split.py` делал случайный сплит по строкам, из-за чего одна тема попадала в train и test.

**Как проявлялся**: `check_contamination.py` находил `group_overlap > 0`, `near_dup_pairs > 0`.

**Как исправлен**: 
- введён `src/groups.py` с функцией `make_group_key`
- `split.py` использует групповой сплит по `topic_hash` (granularity=10)
- `contamination.py` и `scripts/check_contamination.py` используют ту же функцию

**Числом**: `dvc metrics diff` показывает `contamination.group_overlap: 0`, `contamination.near_dup_pairs: 0` в обеих версиях.

---

## Дефект 4: Near-dup не ловится

**В чём был**: в `clean.py` стоял `# TODO: сюда просится ещё один шаг дедупликации` и `near: set[int] = set()` — стадия near-dup не работала.

**Как проявлялся**: пары почти одинаковых примеров (тот же вопрос, переставленные варианты) переживали очистку.

**Как исправлен**: добавлен вызов `near_duplicates()` из `src/dedup.py` с нормализацией `normalize_text(ex.user)`.

**Числом**: `clean.py` теперь сообщает `near-dup -24` (v1) и `near-dup -38` (v2). В `metrics/clean.json` `dropped_near_dup` = 24/38.

---

## Дефект 5: Гейт разнообразия не падает

**В чём был**: в `diversity.py` стоял `# TODO: гейт или отчёт?` и код только печатал предупреждение `print("diversity: предупреждение — ...")`, не завершая стадию с ошибкой.

**Как проявлялся**: вырожденный набор (1000 строк с одним system-промптом, одной темой, ответами одной длины) проходил пайплайн целиком.

**Как исправлен**: вместо `print` теперь `raise DiversityError(...)` плюс печать каждого нарушения на отдельной строке (для `grep -c` в `check.sh`).

**Числом**: `check.sh` проверка №6 показывает «гейт упал и назвал 4 нарушенных порога».
